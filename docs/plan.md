# 往 Architect 前進：第一期 12 週計畫

> 建立日期：2026-10-21
> 來源：/grill-me 追問共 28 題後達成的共識

## 1. 目標

- **長期**：成為 Architect / Tech Lead，全端是過程
- **這 12 週**：練「做決策、寫下來、說清楚取捨」，不是單純學會寫後端
- **和 AI 的分工**：我先決定設計並寫好 ADR，AI 負責實作；每個決策我都要能解釋，程式我自己改得動

## 2. 專案：互相督促的習慣打卡 App

**使用者**：我和 1 位朋友，組成一個小組，看得到彼此的打卡和連續天數

### MVP 範圍（第 1～4 週）

- Google 登入，用邀請連結加入小組
- 手動快速打卡：運動，加上 1 個自訂習慣（資料模型要能擴充到其他習慣）
- 條件式提醒：到了自己設定的時間還沒打卡，才發 Web Push
- 每週一次小組總結
- 前端做成 PWA，可以安裝到手機主畫面（iPhone 要先加到主畫面才收得到推播）

### 技術選型

| 層 | 選擇 |
|---|---|
| 前端 | Vue，做成 PWA，用 Web Push 提醒 |
| 後端 | Go，modular monolith |
| 資料庫 | PostgreSQL（Neon），MVP 不加 Redis 或 queue |
| 部署 | Cloud Run，Cloud Scheduler 從外部觸發排程（見 [ADR-0001](adr/0001-hosting-and-scheduling.md)） |
| 登入 | Google OAuth / OIDC |
| Repo | 公開 GitHub monorepo：`web/`、`api/`、`docs/adr/` |
| CI/CD | GitHub Actions 跑測試和 lint，合併進 main 後自動部署 |
| 可觀測性 | `slog` 結構化 log、health check endpoint、Sentry 免費方案 |
| 時間 | 一律用 UTC 儲存，每個使用者另外記錄時區 |

**預算**：每月 NT$300 以內，以免費額度為主

### 原則

- 先做 modular monolith，**有真實的理由才拆**，拆的時候寫 ADR 說明原因
- PostgreSQL 撐不住時才加 Redis 或 queue，同樣要寫 ADR
- 用 unique constraint 避免重複發送提醒

## 3. 12 週時程

| 週次 | 主題 | 產出 | 會學到 |
|---|---|---|---|
| 1～4 | MVP 上線 | 可用的 App、ADR-0001～0004 | 全端基礎、OAuth、部署、排程 |
| **5** | **小組挑戰開始日** | 朋友開始使用 | |
| 5～6 | 串接 Strava，用 webhook 自動匯入 | ADR | 外部整合、OAuth、重試、冪等性 |
| 7～8 | 通知加上 LINE 管道，拆出通知服務 | ADR | 模組邊界、什麼時候該拆、服務間溝通 |
| 9～10 | 壓力測試，模擬使用者變 100 倍 | ADR、測試報告 | 索引、cache、找出真正的瓶頸 |
| 11～12 | 故障演練，讓 DB 或通知服務故意掛掉 | postmortem | 韌性設計、降級、事故檢討 |

第 5～12 週的順序可以依照朋友的實際回饋調整，但每個主題都要留下 ADR 或 postmortem。

### 第 1～4 週拆解

- **第 1 週**：決定資料模型（使用者、小組、習慣、打卡紀錄、提醒），寫 ADR；建立 monorepo 和 CI；Go 專案骨架、health check、`slog`
- **第 2 週**：Google 登入、小組和邀請連結、打卡 API；Vue PWA 的基本畫面
- **第 3 週**：部署到 Cloud Run 和 Neon；接上 Sentry；Web Push 訂閱
- **第 4 週**：條件式提醒和每週總結（依照 ADR-0001 的排程設計）；自己先用一週，修掉問題

## 4. 每週時間分配（6～8 小時）

| 時間 | 做什麼 |
|---|---|
| 1 小時 | 讀理論：DDIA 一週一章，並套用到專案上 |
| 1 小時 | 寫設計：ADR、資料模型、API 規格，**寫完才讓 AI 開始實作** |
| 4～5 小時 | 實作、review AI 寫的程式、部署 |
| 30 分鐘 | 寫週記：做了哪些決定、AI 哪裡寫錯了、學到什麼 |

## 5. 在公司同步進行

- **前 4 週內**：畫出公司系統的架構圖（前端、後端、資料庫、外部服務），找後端同事或 Tech Lead 對答案

## 6. 使用者

- **這週內**：約好朋友，告訴對方第 5 週是小組挑戰開始日
- **第 8 週前**：請朋友用邀請連結再拉一個人進來，順便測試邀請流程；拉不到人也不算失敗
- 人數少造成的「缺乏真實壓力」，由第 9～10 週的壓力測試補上

## 7. 成功標準（第 12 週檢查）

- [ ] 2 個人**連續 4 週**都有在用
- [ ] 至少 **8 份 ADR** 和 **1 份 postmortem**
- [ ] 能在 **15 分鐘內**，把整個系統的架構和取捨講給一位資深工程師聽，並且回答得了追問
- [ ] 公司系統的架構圖已經和後端同事或 Tech Lead 對過答案

即使專案沒有變成很厲害的產品，只要達到以上標準，這一期就算成功。
